# 核心概念

本文介绍 goal-studio 的核心设计概念,理解这些概念是高效使用与扩展系统的基础。

## 三层 DAG

goal-studio 将一个用户目标转化为**三层有向无环图(DAG)**,每一层对应不同的抽象粒度,自顶向下逐步精化。

### L1 任务规划层

L1 负责将自然语言目标拆解为可执行的子任务序列。每个 L1 节点是一个粗粒度任务,描述"做什么",不关心"谁来做"或"怎么做"。

- 输入:`GoalContract`
- 输出:子任务列表与依赖关系
- 示例:`创建一个网页总结 skill` → `[抓取网页, 提取正文, 生成摘要, 封装 skill]`

### L2 Agent 分配层

L2 为每个 L1 任务分配执行 Agent 与所需工具。此层决定"谁来做",并标注每个 Agent 的输入产物与输出产物类型。

- 输入:L1 任务节点
- 输出:Agent 绑定关系与工具集
- 关键约束:Agent 的输入产物必须与上游 Agent 的输出产物类型兼容

### L3 节点精化层

L3 将每个 L2 Agent 节点展开为具体的执行步骤,包含 prompt 模板、参数绑定与异常处理策略。此层是最细粒度,直接对应一次 LLM 调用或工具调用。

- 输入:L2 Agent 节点
- 输出:可执行节点(含 prompt、参数、超时配置)

::: tip 层级关系
三层之间是**包含关系**:L1 ⊃ L2 ⊃ L3。任意 L3 节点都可回溯到其所属的 L1 任务与 L2 Agent,便于根因定位。
:::

## GoalContract 四要素

`GoalContract`(目标契约)是 goal-studio 的输入入口,用四个要素完整描述一个目标。系统依据该契约驱动整个 DAG 生成与验证流程。

| 要素 | 字段 | 说明 |
| --- | --- | --- |
| 目标 | `goal` | 用自然语言描述最终要达成的事情 |
| 前置条件 | `prerequisites` | 启动前必须满足的条件(环境、数据、权限) |
| 约束 | `constraints` | 执行过程中必须遵守的边界(成本、时长、规范) |
| 成功标准 | `success_criteria` | 可验证的完成判定条件 |

示例:

```yaml
goal: 创建一个可以总结网页内容的 skill
prerequisites:
  - 已安装 Python 3.10+
  - 已配置 OPENAI_API_KEY
constraints:
  - 单次总结成本不超过 0.01 美元
  - 总结耗时不超过 5 秒
success_criteria:
  - 输出包含不超过 200 字的摘要
  - 摘要覆盖原文核心观点
  - 产物可通过 skill 适配器构建
```

::: warning 成功标准必须可验证
`success_criteria` 会被 `verify` 命令自动校验。请避免使用"质量好"这类主观描述,改用可量化或可断言的条件。
:::

## 产物类型与适配器

goal-studio 的最终输出称为**产物(Artifact)**。系统内置四种产物类型,每种类型由对应的**适配器(Adapter)**负责构建。

| 产物类型 | 适配器 | 说明 |
| --- | --- | --- |
| `skill` | SkillAdapter | 打包为可复用的 AI 技能(含 prompt、工具、元数据) |
| `code` | CodeAdapter | 生成可执行代码模块 |
| `doc` | DocAdapter | 生成结构化文档 |
| `workflow` | WorkflowAdapter | 生成可编排的工作流定义 |

适配器遵循统一接口,接收 L3 节点产物并输出标准化的产物包。开发者可自定义适配器扩展新的产物类型,详见 [适配器开发](./adapter-dev)。

::: tip 适配器选择
产物类型在 `GoalContract` 中通过 `artifact_type` 字段指定。一个 DAG 可包含多种产物类型,由不同 L2 Agent 分别产出。
:::

## 棘轮门控

**棘轮门控(Ratchet Gate)**是 goal-studio 的质量保障机制,核心原则是**分数只升不降**。

### 工作原理

每次 `refine` 或 `build` 后,系统会对产物打分并记录。新分数必须**大于等于**历史最高分,否则变更被拒绝回滚。

```
历史最高分: 85
本次 refine 后分数: 88 → 通过,更新最高分为 88
本次 refine 后分数: 82 → 拒绝,回滚到 88 版本
```

### 双评审仲裁

分数由两路评审器独立给出,通过仲裁机制融合:

1. **规则评审器**:基于静态规则(结构完整性、命名规范、必填字段)给出分数
2. **LLM 评审器**:基于语义理解(逻辑合理性、覆盖度)给出分数

当两路分数差异超过阈值时,触发仲裁策略(取较高分 / 人工介入)。

::: warning 棘轮不可降级
棘轮门控一旦记录最高分,任何低于该分数的变更都会被自动回滚。如需主动降级(例如修复严重缺陷),需使用 `goal-studio refine --force` 并记录降级原因。
:::

## 五层意图解析

goal-studio 通过**五层流水线**将自然语言目标解析为可执行 DAG,每一层有明确的输入输出与职责边界。

```
采集 → 对齐 → LLM解析 → 节点消解 → 动作执行
```

### 1. 采集层

从用户输入(文本、语音、文件)中提取原始意图片段,不做语义理解,只做格式归一化。

### 2. 对齐层

将采集到的意图片段与当前 DAG 上下文对齐,识别新增、修改、删除三类操作意图。

### 3. LLM 解析层

调用大模型将对齐后的意图转化为结构化的 DAG 节点描述(JSON Schema),包含任务、Agent、节点三层信息。

### 4. 节点消解层

将 LLM 输出的抽象节点描述映射到具体可执行节点,解析工具引用、参数绑定与依赖关系。

### 5. 动作执行层

按拓扑序执行 DAG 节点,产出最终产物,并触发棘轮门控校验。

::: tip 流水线可中断
每一层都支持中断与恢复。LLM 解析失败时,系统会保留前两层结果并提示用户修正输入,无需从头开始。
:::

## 语音流接入

goal-studio 支持语音输入,采用**增量解析**策略,实时反馈识别进度。

### Chunk 类型

语音流被切分为两种 chunk,系统对不同类型采取不同处理策略:

| Chunk 类型 | 说明 | 处理策略 |
| --- | --- | --- |
| `interim` | 临时识别结果,可能被后续覆盖 | 仅更新 UI 显示,不触发 DAG 变更 |
| `final` | 最终识别结果,稳定不变 | 进入五层意图解析流水线 |

### 增量解析流程

```python
async for chunk in voice_stream:
    if chunk.type == "interim":
        # 实时更新界面文字,不入流水线
        ui.update_transcript(chunk.text)
    elif chunk.type == "final":
        # 进入五层解析,可能触发 DAG 增量更新
        await intent_pipeline.feed(chunk.text)
```

::: tip 性能优化
`interim` chunk 频率较高(通常每 100ms 一次),务必避免在其中执行重计算。所有代价高昂的操作都应推迟到 `final` chunk 到达后执行。
:::

::: warning 多句合并
连续多个 `final` chunk 可能表达同一个意图。对齐层会维护一个时间窗口,合并相邻 chunk 后再进入 LLM 解析,避免生成碎片化 DAG。
:::
